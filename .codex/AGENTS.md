# Instructions for Codex

These rules apply to the entire repository.

# Правила работы над проектом

Ты работаешь над игровым проектом на Godot, условно называемым Zelda-клоном.

## Главная цель

Выполняй только конкретную задачу, которую я поставил в текущем сообщении.

Не перерабатывай проект целиком, не проводи общий рефакторинг и не улучшай код, который напрямую не относится к задаче.

Главные приоритеты:

1. Минимальные изменения.
2. Минимальное использование токенов.
3. Сохранение существующей архитектуры и поведения проекта.
4. Последовательное выполнение задач.
5. Отсутствие самовольных дополнений.

## Порядок работы

Для каждой новой задачи работай в два этапа.

### Этап 1. Анализ и план

Сначала:

- найди только файлы, непосредственно связанные с задачей;
- не изучай весь репозиторий без необходимости;
- кратко опиши причину проблемы или способ реализации;
- перечисли файлы, которые потребуется изменить;
- составь короткий план из нескольких шагов;
- укажи, что мне потребуется вручную сделать в редакторе Godot.

До составления плана не изменяй файлы.

План должен быть кратким и практическим. Не пересказывай очевидное и не пиши длинные объяснения.

### Этап 2. Реализация

После плана выполняй задачу последовательно.

Во время реализации:

- изменяй только необходимые файлы;
- не меняй несвязанный код;
- не переименовывай существующие узлы, ресурсы, сцены, методы и переменные без прямой необходимости;
- не выполняй массовое форматирование;
- не перестраивай архитектуру;
- не добавляй новые системы «на будущее»;
- не добавляй дополнительные настройки, эффекты или возможности, которых я не просил;
- не создавай альтернативные реализации одной функции;
- не оставляй лишние временные файлы;
- не запускай длительные проверки всего проекта, если достаточно проверить изменённую часть.

Если задача может быть решена небольшим локальным изменением, используй именно его.

## Разрешённая работа

Ты можешь:

- писать и изменять GDScript;
- создавать новые `.gd`-скрипты, когда они действительно нужны;
- писать небольшие Python-скрипты для автоматизации;
- добавлять минимально необходимые конфигурационные или текстовые файлы;
- анализировать ошибки;
- исправлять баги;
- давать точные инструкции по настройке сцены в Godot.

## Что нельзя делать

Без моего прямого указания нельзя:

- создавать или редактировать графические ассеты;
- создавать звуки, музыку или анимационные ресурсы;
- перемещать объекты и узлы в сценах;
- менять визуальное расположение элементов;
- самостоятельно редактировать уровни;
- массово изменять `.tscn` и `.tres`;
- импортировать ассеты;
- заменять существующие ресурсы;
- добавлять контент от себя;
- менять игровой баланс;
- добавлять новые механики;
- улучшать интерфейс;
- проводить общий рефакторинг;
- обновлять зависимости, плагины или версию Godot;
- коммитить или пушить изменения;
- создавать pull request.

Если для работы требуется действие в редакторе Godot, не пытайся имитировать его через массовое редактирование файлов сцены. Вместо этого напиши мне короткую пошаговую инструкцию.

## Работа со сценами Godot

По возможности не редактируй `.tscn` вручную.

Если требуется:

- добавить узел;
- поменять позицию;
- назначить ресурс;
- подключить сигнал;
- изменить Inspector;
- добавить AnimationPlayer;
- настроить CollisionShape;
- назначить скрипт;
- добавить Input Map action;

то напиши мне точные действия для выполнения в редакторе Godot.

Формат инструкции:

1. Открой сцену `название`.
2. Выбери узел `название`.
3. Добавь дочерний узел `тип`.
4. В Inspector установи `параметр = значение`.
5. Подключи сигнал `название` к методу `название`.

Не объясняй интерфейс Godot подробнее, чем необходимо.

## Экономия токенов и контекста

Всегда придерживайся следующих правил:

- сначала используй поиск по именам файлов, классов, методов и узлов;
- не открывай большие файлы полностью, если достаточно нужного участка;
- не анализируй все сцены и скрипты проекта;
- не пересказывай содержимое прочитанных файлов;
- не показывай полностью файл, если изменено несколько строк;
- не повторяй мой запрос;
- не пиши длинные вступления;
- не перечисляй действия, которые не выполнялись;
- не предлагай дополнительные улучшения;
- не создавай документацию без запроса;
- не добавляй комментарии в очевидный код;
- не запускай одинаковые команды повторно без причины.

Если информации недостаточно, сначала попробуй получить её из ближайших связанных файлов. Не исследуй весь проект.

Если существует несколько вариантов решения, выбери наиболее простой, локальный и совместимый с текущим кодом. Кратко упомяни выбранный вариант, не составляя длинное сравнение.

## Требования к коду

Код должен:

- соответствовать текущему стилю проекта;
- быть совместимым с используемой версией Godot;
- не ломать существующий публичный интерфейс скриптов;
- содержать только необходимую логику;
- не включать абстракции ради абстракций;
- не дублировать существующие системы;
- использовать существующие компоненты проекта, если они подходят для задачи.

Перед созданием нового скрипта сначала проверь, нельзя ли внести небольшое изменение в существующий.

## Проверка результата

Проверяй только то, что относится к текущей задаче.

После реализации:

- проверь изменённые скрипты на очевидные синтаксические ошибки;
- перечисли, что именно было изменено;
- сообщи, что не удалось проверить без запуска редактора;
- дай короткую инструкцию для ручной проверки в Godot.

Не заявляй, что задача полностью работает, если она не была реально проверена.

## Формат итогового ответа

В конце каждой задачи используй строго такой формат:

### Изменено

- `путь к файлу` — краткое описание изменения.

### Что сделать в Godot

1. Только необходимые ручные действия.
2. Если ручных действий нет, напиши: `Ничего`.

### Как проверить

1. Короткие шаги проверки результата.

### Коммит

`тип: краткое описание изменения`

Пример:

`fix: smooth player roll collision recovery`

Коммит должен быть на английском языке, одной строкой, без точки в конце.

Допустимые префиксы:

- `feat:` — новая функциональность;
- `fix:` — исправление ошибки;
- `refactor:` — рефакторинг, только если я его прямо запросил;
- `chore:` — техническое изменение;
- `perf:` — оптимизация;
- `docs:` — документация.

Не выполняй сам `git commit`, `git push`, создание ветки или pull request. Я самостоятельно коммичу изменения и отправляю их через Fork.

## Поведение при расширении задачи

Если во время работы обнаружена другая проблема:

- не исправляй её;
- кратко упомяни её в конце;
- продолжай выполнять только текущую задачу.

Если запрошенное изменение требует значительно более крупной переработки, сначала сообщи об этом в плане и предложи минимальный вариант. Не начинай масштабную переработку самостоятельно.

## Основное правило

Не делай проект «лучше» в целом.

Сделай только то, что я попросил, минимальным безопасным изменением.
